# mp-weixin-back 代码评审报告

> 评审日期：2026-07-03
> 评审范围：`src/`、`utils/`、`types/`、`test/`、CI 配置（基于 main 分支 440d4d5）
> 结论：编译期注入 + 虚拟模块的整体架构合理，但存在若干正确性隐患和架构改进空间。
> 按优先级分为三档，每项标注问题位置、失败场景与修复建议。

---

## 一、高优先级：正确性问题

### 1.1 构建期用 `new Function` 执行用户代码

**位置**：`utils/walker.ts:93`

`onPageBack(fn, { ... })` 的第二个参数被 generate 成字符串后用 `new Function` 求值。

**失败场景**：用户传入任何非字面量——如 `{ frequency: myVar }`、`{ preventDefault: import.meta.env.DEV }`——构建期直接 `ReferenceError` 崩溃，且报错信息不可读。

**建议**：静态提取字面量属性（遇到非字面量给出友好报错），或把对象表达式源码原样拼进生成代码、让它在运行时求值。

### 1.2 全局 `onPageBack` 用 `toString()` 序列化，闭包丢失

**位置**：`utils/walker.ts:210`、`utils/walker.ts:213`

vite.config 里传入的全局回调函数被字符串化后注入页面代码。

**失败场景**：
- 函数体引用任何闭包变量（配置文件里 import 的模块、外层变量），运行时 `ReferenceError`，且失败是静默的。
- shorthand method 分支 `(function ${onPageBack})()` 没有传 `params`，用户写成 `onPageBack({ page }) {...}` 时参数为 `undefined`——这是一个直接的 bug。

**建议**：至少在文档中说明"函数必须自包含"；修复 shorthand 分支的参数传递；检测到可疑闭包引用时给出构建期警告。

### 1.3 未按平台门控注入

**位置**：`src/index.ts`（transform 钩子全局生效）

`page-container` 是微信小程序专属组件，但插件在 H5 / App / 其他小程序平台的构建中同样注入模板和 `uni.navigateBack` 逻辑。

**建议**：在 `configResolved` 中读取 `process.env.UNI_PLATFORM`，非 `mp-weixin` 时 transform 直接跳过；虚拟模块保留 no-op 导出以保证代码可编译。

### 1.4 `buildStart` 未 await，存在竞态

**位置**：`src/index.ts:24`、`src/context.ts:30`

- `context.getPagesJsonInfo()` 是 async 但未 return/await，transform 可能在 pages 列表加载完成前执行。`buildStart` 支持返回 Promise，改为 `return context.getPagesJsonInfo()` 即可。
- dev 模式下 pages.json 变更无 watcher（可用 `this.addWatchFile`）。
- `src/pages.json` 路径硬编码，不兼容 HBuilderX 创建的项目（pages.json 在项目根目录）。

### 1.5 `active/inactiveMpBack` 调用改写用正则，嵌套括号即坏

**位置**：`utils/walker.ts:260`、`utils/walker.ts:275`

用 `` `${call.name}\\(([^)]*)\\)` `` 匹配调用，`[^)]*` 遇到参数内的括号会截断。

**失败场景**：`activeMpBack(() => foo(1))` 会生成损坏的代码。

**建议**：已有精确的 AST `start/end`，直接在 `start + name.length + 1` 位置插入 `__MP_WEIXIN_ACTIVEBACK__, `，不需要正则。另外当前只匹配 `ExpressionStatement` 级别的调用，`ok && activeMpBack()`、`const r = activeMpBack()` 会被漏掉。

### 1.6 标识符匹配方式脆弱

**位置**：`utils/walker.ts:85`、`utils/walker.ts:47`

- 用 `callee.loc?.identifierName` 判断调用名，`loc` 不保证存在。应改为 `callee.type === 'Identifier' && callee.name === ...`。
- 未校验 binding 确实来自 helper 的 import，本地定义的同名 `onPageBack` 函数会被误处理。
- import source 判断用 `includes(virtualFileId)`，`'mp-weixin-back-helper-v2'` 这类包名会误中，应改为全等比较。

## 二、中优先级：架构改进

### 2.1 transform 无快速跳过，所有 .vue 文件全量解析

**位置**：`src/index.ts:67`

每个 .vue 文件都要走 compiler-sfc parse + babel parse，即使根本没使用 helper（`hasPageBack` 的判断发生在完整 AST 遍历之后）。

**建议**：
- 加一行 `if (!code.includes(virtualFileId)) return`，可跳过绝大多数文件，对大项目是数量级的构建提速。
- `id.includes('.vue')` 会误中 `xxx.vue?vue&type=script` 等子请求和 `.vue.ts` 文件，应剥离 query 后判断扩展名，或使用 Vite 的 `createFilter`。

### 2.2 optionsAPI 路径整段重写 script，且与 composition 路径行为不一致

**位置**：`utils/walker.ts:517`、`utils/walker.ts:377`

- 用 `@babel/generator` 重新生成整个 `<script>`：原始格式丢失、sourcemap 只能映射到块级，与 composition 路径（MagicString 增量编辑）是两套完全不同的策略。
- `initialValue` 配置被忽略（data 中硬编码 `true`）。
- 不支持 per-page options。
- 原有的 `onPageBack() {}` 方法未从组件选项中移除，留在产物里成为死代码。
- `configBack` 生成逻辑在两个 walker 中各复制了一份（`walker.ts:203`、`walker.ts:428`）。

**建议**：统一为 MagicString 插入式改写，两条路径共享一套"生成注入代码"的逻辑，对齐行为差异。

### 2.3 sourcemap 精度问题

**位置**：`utils/walker.ts:240`、`utils/walker.ts:288`

composition 路径先构造嵌套 MagicString、再 `overwrite` 整个 template/script 块，overwrite 整块会把该区域的映射压成一个点。

**建议**：所有编辑位置都能换算成全局 offset，直接在外层 `codeMs` 上做 `appendLeft` / `prependRight` / `remove`，保住逐行映射。

### 2.4 未将 transform 限定在"页面"上

**位置**：`src/context.ts:70`

- `context.pages` 目前只用于日志和回调参数，组件（非页面）里 import helper 同样会被注入 `page-container`，而微信只允许页面级使用，运行时静默失效。应在 transform 中用 `getPageById(id) === null` 跳过并警告。
- `id.split('src/')[1]` 取第一个 `src/`，项目路径本身含 `src/`（如 `/home/x/src/app/src/pages/...`）时解析错误，改用 `path.relative` 更稳。

### 2.5 错误被静默吞掉

**位置**：`utils/index.ts:54`、`src/index.ts:39`

- transform 的 catch 返回原 code，构建照常成功，用户只能在运行时发现拦截不生效。
- 虚拟模块的 fallback `onPageBack() {}` 同样零反馈。

**建议**：dev 模式下错误显眼输出（可通过 `this.error` 让 Vite overlay 展示）；运行时 no-op 版本加一句 dev 警告；未命中时返回 `undefined` 而不是 `{ code, map: null }`，语义上告诉 Vite "未修改"，同时避免 sourcemap 告警。

### 2.6 虚拟模块未遵循 Rollup 约定

**位置**：`src/index.ts:28`

`resolveId` 返回裸 id。约定是返回 `'\0' + virtualFileId`，`load` 中匹配带前缀的 id，防止其他插件（尤其 optimizeDeps）把 `mp-weixin-back-helper` 当 npm 包去解析。

## 三、低优先级：工程化

### 3.1 CI 缺测试关卡

`publish.yml` 只有发布流程，`pnpm release` 也不跑测试。建议增加 PR/push 触发的 test + typecheck workflow，并在 release 脚本中前置 `pnpm test run`。

### 3.2 测试覆盖薄

目前只有 3 个 happy-path 用例。最值得补充的：

- per-page options（`preventDefault` / `frequency` / `initialValue`）
- `frequency` 的实际拦截次数——当前计数从 1 起、条件是 `< frequency`，语义上疑似 off-by-one，值得用测试钉死
- subpackages 解析
- import 别名（`import back from '...'`）
- options API 的 `onPageBack: function() {}` 写法

也可考虑直接对 transform 输出做快照测试，比挂载组件更能覆盖生成代码的形态。

### 3.3 目录与命名

- `utils/`、`types/` 放在 `src/` 外不符合常规。
- `pageContext` 类名应大写（`PageContext`）。
- `src/index.ts:73` 的 `as Plugin` 强转会掩盖钩子签名的类型错误，去掉让 TS 真正检查。

### 3.4 可配置性

`utils/walker.ts:17` 注入的 `page-container` 的 `z-index`、`duration` 硬编码，可开放到插件配置。

---

## 四、建议的整改顺序

1. **transform 快速跳过 + id 过滤修正**（2.1）——收益最大、改动最小，性能与误伤一次解决。
2. **移除构建期 `new Function` 求值与函数 `toString()` 序列化**（1.1、1.2）——消除"一碰闭包/变量就炸"的两处机制性风险。
3. **统一两条 walker 路径为 MagicString 增量编辑并对齐行为差异**（2.2、2.3）——去重、修 sourcemap、消除 API 行为不一致。
4. 其余项（平台门控、竞态、正则改写、虚拟模块约定）可随上述改动顺带处理。
5. 每修一项补一个对应测试用例，并把 test + typecheck 挂进 CI（3.1、3.2）。
